# Independent audit plan — nuthatch v3.1.0

**For an auditor who did not write this code.** Commissioned 2026-09-01 precisely because the people
who did are poor judges of it: most of the recent work was authored and reviewed in the same sitting,
and the reviewer that found ~29 of 31 real defects in the last two sprints was an outside one. Every
"clean" result below was produced by someone looking where they expected clean.

Read `CLAUDE.md` first. It is the standing brief and it constrains what a finding may recommend.

## What "a finding" means here

This project's house rule, learned the hard way and repeatedly: **a test that passes proves nothing
until it has been made to fail.** The same standard applies to your findings.

A finding is worth filing when you can state:

1. **The failure scenario** — concrete inputs or state, and the wrong output or behaviour. Not "this
   could be unsafe".
2. **The evidence** — a command someone else can run, its output, or a mutation that goes red.
3. **Why it is not already caught** — which test or gate should have found it, and what it asserts
   instead.

Findings without (3) are the most valuable ones this codebase has received. Several of its tests
assert the *comment* next to the code rather than the code.

**Anything worth remembering must become a GitHub issue.** A conclusion in a report nobody can find
is a conclusion nobody will act on.

## Where the bias is, explicitly

Do not treat any of this as settled. It is where I looked, and how, so you can look differently:

- I grepped `src/serve.rs`, `src/analytics.rs`, `src/store.rs` for `unwrap`/`expect`/`panic!` outside
  test modules and found **0, 0, and 0**. That is a grep, not an analysis: it says nothing about
  panics in dependencies (DuckDB, Arrow, parquet, dbsp) reached through those paths, arithmetic
  overflow in release builds, slice indexing, or `RefCell`/lock poisoning.
- There is **no `CatchPanicLayer`** on the router. I judged this low value because the direct paths
  are clean. That judgement is exactly the kind I am bad at.
- I found `cargo deny check advisories` clean and stopped. I did not audit transitive dependencies
  for unmaintained crates, licence drift, or crates with a single maintainer.
- Default binds are `127.0.0.1` and admin routes are gated on a public bind without a token. I read
  the comment saying so and one test name. I did not try to defeat it.
- I checked HTTP limits and found SQL concurrency, row cap and timeout bounded. I did **not** check
  request body limits, header limits, slow-loris behaviour, or what a 100 MB query string does.

## Scope, in priority order

### 1. Security and hardening

The product is **self-hosted-first** and binds a network listener. Assume an operator exposes it
carelessly, because they will.

- **The `/sql` surface.** It takes user SQL. `src/analytics.rs` has a parser-derived allowlist —
  `CLAUDE.md` notes it is the *only* guard in the repo built that way, the rest being denylists over
  a growing vocabulary. Try to defeat it: attached databases, `COPY`, `INSTALL`/`LOAD`, file
  functions (`read_csv`, `read_parquet` on a path you choose), `pragma`, recursive CTEs as a DoS.
  **DuckDB is attached read-only; verify that claim rather than accepting it.**
- **Path handling.** `--dir`, mounts, `data/<nid>/`, segment paths. A nest alias or NID that
  traverses. What a symlink in a nest directory does.
- **The admin surface.** Actually try to reach `/_admin*` on a public bind. `--no-admin` promises the
  routes are never registered; check the promise, not the comment.
- **Resource exhaustion.** Body and header limits, concurrent connection limits, a query that
  allocates before the row cap applies, the 30s SQL timeout under a query DuckDB cannot interrupt.
- **Dependencies.** Beyond advisories: unmaintained crates, licence compliance (`MIT OR Apache-2.0`
  core, and `deny.toml` forbids GPL/AGPL — verify it actually forbids), and anything pulling network
  at build time.
- **Secrets.** RPC URLs and API keys in configs, logs, error messages, and `/metrics`. An RPC URL
  with an embedded key that appears in a log line is a real leak.

### 2. Correctness

The non-negotiable is **determinism**: ABI decoding, reorg handling, entity derivation and anything
feeding stored state must be re-executable to the same result.

- **Reorg handling.** Property tests exist; try to find a depth or interleaving they do not cover.
  Reorgs must touch only the hot store, never sealed segments.
- **Segment identity.** Sealing must cut at boundaries chosen *from the data*, so the same rows
  produce the same segments under any `--window` or `--concurrency`. **The test guarding this greps a
  comment** (see #1068) — the property is currently unprotected.
- **`i128`/`u256` arithmetic.** Overflow paths were recently found unchecked (#998). Look for others.
- **The DBSP entity circuit.** Retraction on reorg, backfill as a batch run of the same circuit.

### 3. Performance

Benchmarks are CI artefacts and regressions fail the build; the interesting question is what is *not*
measured.

- **Segment layout.** 80% of segments are under 20 KB because the tip path does not batch (#1067).
  Quantify the query cost at production scale.
- **The 2 GB per-cursor RAM budget.** Two cursors sit at ~1352 MB and nobody knows where it goes
  (#1069). Two hypotheses have been measured and **both were wrong**, including one whose synthetic
  benchmark had the sign inverted. Profile rather than reason.
- **Hot paths.** Decode, `commit_window`, point reads. Allocation per row, and anything O(n²) in a
  loop over blocks or logs.

### 4. Usability — the delightful core (RFC-0015)

Explicitly in scope under the 2026 freeze, and the least measured thing here.

- **Run the 90-second promise cold.** `curl | sh` → `init` → `dev` → a query, on a clean machine,
  with a stopwatch. The claim is under two minutes to first indexed query.
- **Error messages.** Take the twenty most likely operator mistakes — wrong chain, bad ABI, dead RPC,
  a nest that is already running, a full disk — and judge whether the message names the cause and a
  next step. Several were recently found to name neither.
- **The CLI surface.** Flags that exist and are undocumented, documented flags that do not exist,
  and `--help` text that describes an older behaviour.

### 5. Documentation and claims

Every published number must trace to something reproducible. `docs/verification.md` has a
"verified-by-us" table; check it is honest.

- Claims in `README.md`, `docs/`, and the website (a separate repo, see #1072) against **3.1.0**
  behaviour.
- Benchmarks quoted without a date, a box, or a method.

## 6. The Lodestar migration — audit the *scope*, not just the code

A second job, and a different kind: **check whether the migration is completely scoped in issues.**
The scoping below was done on 2026-09-01 by the same person writing this plan, in an afternoon, and
is therefore exactly the sort of thing that should not be taken on trust.

Lodestar is Night's Watch code (`~/Projects/lodestar`), on our own machines. The goal is that its data
comes from nuthatch nests rather than from subgraphs through The Graph's gateway.

### The architecture, as understood

```
subgraph APIs  ->  scripts/cron-runner.ts (droplet, system cron)  ->  Postgres  ->  Next.js UI
```

The UI mostly reads **Postgres**. So the migration seam is the *ingestion layer*, not the API routes -
a conclusion reached only after first writing the issue the other way round.

### What the sweep found

37 files touch the gateway; 35 reference nuthatch, all of them downstream of ingestion. **Every one of
the nine ingestion modules has zero nuthatch references** - the migration has not begun where it
matters.

| module | gateway refs | nest view |
| --- | ---: | --- |
| `allocations.ts` | 11 | `40-lodestar-allocations.sql` |
| `epochs.ts` | 3 | `50-lodestar-epochs.sql` |
| `disputes.ts` | 6 | `60-lodestar-disputes.sql` |
| `network-snapshot.ts` | 6 | `80-lodestar-network.sql` |
| `rav.ts` | 4 | `70-lodestar-escrow.sql` |
| `delegations.ts` | 2 | **none** |
| `refresh.ts` | 17 | **none** |
| `qos.ts` | 26 | **none, probably out of remit** |
| `indexers.ts` | 0 | reads Postgres |

Open issues: **#1074** (inventory), **#1075** (`graph-allocations-nest` is deployed nowhere),
**#1076** (continuous parity), **#1077** (undocumented nest dirs), **#1078** (migrate ingestion),
**#1079** (document intended gateway use), **#1080** (behaviour when a nest is down), **#1081**
(GraphOps handover), **#1082** (`delegations` gap), **#1083** (classify `qos.ts`).

### Where this scoping is most likely wrong

- **The per-surface table in #1074 is a first pass.** Nine test files were discounted **by filename**
  and never opened. The individual GraphQL queries inside each ingestion module have **not** been
  read, so which modules migrate is known and what each one asks for is not.
- **`qos.ts` was classified as probably out of remit without being read.** It is the largest single
  consumer at 26 references; if that judgement is wrong the completion figure is wrong by a visible
  margin. Some of what feeds a QoS view - indexer allocations, stake, registered URL - *is* on chain.
- **Group A of #1074 was classified from docstrings**, not from the code. "This feature's subject is
  the gateway" is a strong claim to make from a comment, in a repo where tests asserting comments is
  a recurring finding.
- **Two issues were filed wrong and corrected within the hour** (#1078's seam, #1082's escrow half).
  Assume there is a third.

### What to check

1. **Is anything missing?** Read `cron-runner.ts`, `src/lib/ingest/*`, `src/lib/refresh.ts` and the
   `scripts/backfill*.ts`, and find a migration-relevant thing with no issue. That is the primary
   deliverable of this section.
2. **Is anything classified wrongly?** Especially `qos.ts` and group A. Getting a surface into "out of
   remit" that could be migrated makes the goal look closer than it is.
3. **Is the Postgres schema a gap?** Whether nest-shaped rows land in the existing tables unchanged
   was never checked. If there is work there, it has no issue.
4. **Does the completion claim survive?** The stated goal is *"no `GRAPH_API_KEY` needed for any
   surface that shows network state"* - explicitly not zero `GRAPH_API_KEY`, because a subgraph
   playground with no subgraph is a deleted feature rather than a migrated one. Check that this is
   the honest framing and not a convenient one.

## Deliverable

One GitHub issue per finding, with the three elements above. A short summary document listing what
you examined and — **as valuable** — what you examined and found sound, so the next audit does not
repeat it.

Where you find nothing, say so plainly. "I tried to defeat the SQL allowlist for two hours and could
not" is a useful result and will be believed. A clean report with no method described will not be.
