## The August number was right, and it is no longer the number

The audit recorded **~122,000 RPC per HTTP request served**. It is now **659**. That is a 185x
improvement and **almost none of it is ours**:

| | Aug 2026 audit | 2026-08-31 |
| --- | ---: | ---: |
| RPC per **active tip-following** nest per day | ~410,000 (4 nests) | ~505,000 (5 nests) |
| ...of which **steady-state tip-following** | - | **~212,000** (see below) |
| RPC per day, all listed nests | ~1,640,000 | 2,523,389 |
| HTTP served per day, all nests | ~13.5 | **3,828** |
| ratio | 122,000 : 1 | 659 : 1 |

The first row divides by the nests that actually follow tip - four in August, five now. It excludes
`graph-staking-legacy-history`, which makes **zero** RPC calls; averaging it in would give 420,565
and compare an average over five tip-followers against an average over six mixed nests. Both the
label and the divisor are stated because the August comparison only means anything like for like.

**The RPC cost per nest did not fall. Demand arrived.** The ratio was catastrophic because nobody was
querying, and it is respectable now because somebody is. Both readings describe the same product.

**That is the durable finding**: tip-following cost is a constant, independent of demand. A nest that
nobody reads costs the same as one under load. `docs/` already carries the standing note that a parked
nest burns real money; this puts a current number on it.

The clean contrast is on the same box. **`graph-staking-legacy-history` (8103) serves 162 requests for
0 RPC calls** - a read-only nest over sealed history, paying nothing to exist. Every RPC call in the
table above buys tip-following, not serving.

## Where the calls go

`graph-staking-nest`, over the same window:

| method | calls | share |
| --- | ---: | ---: |
| `eth_getBlockByNumber` | 532,646 | **59.9%** |
| `eth_blockNumber` | 178,945 | 20.1% |
| `eth_getLogs` | 178,085 | 20.0% |

**`eth_getBlockByNumber` is 60% of the bill**, and it is the block-timestamp fetch - one header round
trip per block carrying rows.

### The obvious lever is closed

`block_timestamps = false` would remove that 60%. It is not available here:

- **Three of `graph-allocations-nest`'s eight views use `block_timestamp`** - 12 references across
  `40-lodestar-allocations.sql`, `60-lodestar-disputes.sql` and `70-lodestar-escrow.sql`.
- Flipping it is a **breaking schema change** (RFC-0029 §6b): it adds or removes a column on every
  table and changes the bytes of every sealed segment, so existing segments cannot be reused.
  `config.rs` refuses to start on a mismatch. It means a full re-index, not a config edit.

So the 60% is structural for any nest whose views need timestamps. Recorded rather than solved.

## Rate limiting, which the audit did not see

429s in a single hour, by unit:

| unit | endpoint class | 429s/hour |
| --- | --- | ---: |
| `nuthatch` | shared | **44** |
| `nuthatch-gns` | shared | **43** |
| `nuthatch-ds-upstream` | shared | **38** |
| `nuthatch-dips` | shared | 1 |
| `horizon-nest` | paid (Alchemy) | **0** |
| `entity-soak` | - | **0** |

Every unit on the shared endpoint is being rate-limited about **40 times an hour**; the one on a paid
endpoint is not. Each 429 is retried, so the refusals **inflate** the RPC counts above rather than
capping them. The three nests are paying for the same block twice.

This is a cost argument for the paid endpoint rather than only an etiquette one, and it is the
measurement the endpoint decision should rest on.

## Correction: ~505,000/day is not the steady-state cost

That figure averages over a 1.50-day window that begins at a restart, so it contains **catch-up**
as well as tip-following. Measured cleanly on `graph-staking-nest` over a **909-second** window with
the nest already at tip: **2,231 requests, 2.454/s, ~212,000/day** - about **42%** of the windowed
average.

Both numbers are real and they answer different questions. ~505k/day is what a nest costs across a
window that includes catching up; **~212k/day is what it costs to sit at tip**, which is the number
the standing note about a parked nest burning money should use.

The method mix at steady state is unchanged in shape: `eth_getBlockByNumber` **58.4%**,
`eth_blockNumber` 24.8%, `eth_getLogs` 16.8%.

## What changed on the box: all four nests moved onto the Alchemy key

Board decision 2026-08-31. Alchemy was **added to each nest's `rpc_urls`**, the public endpoint left
in place behind it.

**`rpc_urls` is a round-robin pool, not primary-with-fallback.** That is the finding that shaped the
result: adding one endpoint moved roughly **half** the traffic, not all of it.

Measured after the switch, per unit, with 429s counted since each unit's own restart:

| unit | alchemy | public | 429s | lag |
| --- | ---: | ---: | ---: | ---: |
| `nuthatch` | 1,924 | 1,923 | **0** | 0 |
| `nuthatch-gns` | 732 | 732 | **0** | 14 |
| `nuthatch-dips` | 765 | 765 | **0** | 0 |
| `nuthatch-ds-upstream` | 931 | 930 | **0** | 10 |

**429s went from ~40/hour per unit to zero**, and Alchemy recorded **0 failures and 0 retries**
throughout, at a mean latency of roughly 40 ms against the public endpoint's 136 ms.

### The cost, with the arithmetic shown

At ~212,000/day per nest across four nests: **~25.4M requests/month**, of which the pool sends about
half - **~12.7M/month** - to Alchemy.

Weighting the measured method mix by Alchemy's published compute units gives roughly **29.1M CU per
million requests**, so about **370M CU/month**, against a 300M free tier. Comfortably an order of
magnitude below the ~2 billion CU a first estimate produced from the catch-up-inflated rate - which
is the whole reason the rate was re-measured before the change was widened.

### Why the public endpoint was kept in the pool

Removing it would roughly **double** the Alchemy figure for no measured benefit: at the halved load
the public endpoint records **0 failures and 0 retries**. Keeping it is worth ~185M CU/month and
costs nothing observable. Going Alchemy-only remains available and is a cost decision, not a
correctness one.

Every config was backed up before editing, each unit restarted one at a time, and each was required
to answer `/ready` with a 200 before the next was touched.
