## A sparse nest stopped sealing, and nothing said so (#1199)

Both seal paths cut a Parquet segment once 20,000 rows have finalised. That rule alone ratchets shut.
`maybe_seal` reads the finalized range from `sealed_through + 1`, and holds it whenever it carries
fewer rows than the threshold - so the range only ever grows, and the arm that advances the watermark
across a range with no rows becomes unreachable the moment there is one. **A single finalized row
freezes the watermark until twenty thousand have accumulated.**

Measured on the Graph protocol nests behind the Lodestar dashboard, which see roughly 95
event-carrying blocks a day: `sealed_through` had not moved in 739,192 blocks, about 51 hours, while
the cursor sat exactly at tip. It is also why a third nest on the same box, same binary, same minute
of restart, was fine: a range with *no* rows takes the empty arm and tracks finality exactly. The
difference between a nest that sealed and one that did not was one row.

Query answers stayed correct throughout - the hot tier serves the unsealed tail - so what this broke
was provenance rather than data. `sealed_through` is the block a tattler receipt pins, and a receipt
issued from a nest in this state promises an answer computed from history two days older than the one
it was actually given.

**A held range is now also cut at `first_held_row + seal_span - 1`**, whichever comes first. The cut
stays a function of the data and a constant rather than of the clock, so two operators still produce
identical segments (RFC-0028 §4), and both seal paths take the *earlier* of the two candidates so a
backfill holding the whole history cannot disagree with a tip path seeing it a poll at a time.
`maybe_seal` also advances across a leading stretch that carries no rows before it decides anything,
which is what makes the row anchor coincide with the watermark instead of drifting an event gap away
from it.

`seal_span` is per chain, because one number cannot serve both ends: six hours on Arbitrum is eleven
weeks on mainnet, and six hours on mainnet is ninety seconds on Robinhood Chain. Every entry is about
six hours of that chain's block time, from block times measured against the shipped endpoints on
2026-09-07 - mainnet 1,800, Arbitrum One 86,400, Base and Optimism 10,800, BSC 48,000, Polygon 14,400,
Gnosis 4,250, Monad 72,000, Robinhood 216,000. A chain outside the registry gets 10,800. Six hours is
a judgement rather than a measurement: long enough not to cut near-empty segments all day, short
enough that a receipt pins a watermark from within the same working morning.

Nothing already sealed changes, and the content address of a segment is unaffected: it is the hash of
the Parquet bytes, which are built from the rows alone.

## `/ready` can tell a stalled seal from a healthy one

Every seal field on `/ready` described the bulk `--seal-direct` backfill, which on these nests was
never running - so `seal_direct_stalled` read false because no pass had started rather than because
one was keeping up, and `lag_blocks`, which describes *following*, read 0 throughout. A health check
ran against that for days and passed.

- **`seal_lag_blocks`**: how far the sealed watermark trails what the cursor has indexed. Null for a
  `serve`-only role, and null before anything has sealed, since subtracting against the default zero
  would report a healthy nest's first minute as half a billion blocks behind.
- **`tip_seal_stalled`**, and a `stalled` term for it at twelve hours. Chain-independent because
  `seal_span` is sized in time: the bound is written in blocks, but what it buys is a duration. A seal
  that has caught up to its cursor has nothing to do and is not stalled, the same guard `wedged`
  already carries for a cursor at tip.
- **`seconds_since_seal_progress`** is no longer confined to the backfill, because the tip path now
  stamps that clock when the watermark actually advances. It was null on precisely the nests that
  needed it.
