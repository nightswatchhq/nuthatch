The release that makes an `[[ipfs]]` nest over megabyte documents fit to deploy. Every document a nest
names now resolves behind the cursor, is proven against its CID however many blocks it spans, and can
be exploded into typed rows, and a seal cut is bounded by bytes, so sealing those documents stays
inside the memory budget. It was built for Edge & Node's QoS oracle on Gnosis. Beside it come `--cors`
on `dev` and `serve`, `--explorer` on `init` and `add`, `--from-subgraph` over a local
`subgraph.yaml`, and a `doctor` that finds its own probe address. For an events-only nest it is a
binary swap and a restart. A nest that decodes calls, or declares `[[ipfs]]` or `[[calls]]`, should
read the compatibility section first.

## Compatibility and upgrade

**No CLI flag, `nuthatch.toml` key or metric was removed or renamed, and the NID and data identity
are computed as before.** Checked: `git diff v3.7.0..v3.8.0 -- src/cli.rs` adds `--cors` and
`--explorer` and removes nothing; `src/metrics.rs` only adds series; `src/blob.rs`, `src/pack.rs` and
`src/calls.rs` are untouched, so a packed nest's registry hash, its data identity and a published
mirror's prefix do not move; `decode/src/registry.rs` only adds IPFS key constants.

**What moved is the hash the store's identity guard records (#1374).** In 3.7.0 the guard stamped the
event registry's hash alone, while `schema.json` already folded in call extraction, `[[ipfs]]` and
`[[calls]]`. Both now read one function, and the store records which formula it used. For a store
written by 3.7.0:

- **An events-only nest keeps its identity and its data.** Its decode identity is the event registry
  hash, so nothing is re-checked and nothing is re-indexed.
- **A nest with `[[calls]]` or `[[ipfs]]` starts without a re-index.** On its first start the guard
  finds the event-only hash, adopts the full identity once, and logs that the call and `[[ipfs]]`
  declarations were never checked by the old guard. `schema.json` does not change, so a hot upgrade
  still reuses its segments.
- **A nest that has indexed top-level calls must be re-indexed.** Every call row now carries the
  transaction sender as `tx_from`, and that column moves the call registry hash. A store holding call
  rows from before it refuses to start with "Re-index from scratch": remove `nuthatch.redb` and
  `segments/` and let it backfill, or build the new copy beside the old one and swap. A store that
  never indexed a call adopts. A nest with `[extract] traces` also gets a new identity and a new
  `schema.json` hash, so a hot upgrade does not reuse its segments.
- **An `[[ipfs]]` nest that uses none of the new keys keeps its declaration hash**, because
  `cid_json_path`, `json_match` and `[ipfs.rows]` are folded in only when set. Documents a 3.7.0 build
  stored with `verified = false` keep that until the nest is re-indexed; from now on only a proven
  document is written.

Two configurations 3.7.0 accepted now refuse to start:

- **An `[[ipfs]]` name or `[ipfs.rows]` table that is declared twice, or that lands on an event or call
  table.** 3.7.0 started, and read one table's rows with the other's columns.
- **A decoded call with an argument named `tx_from`**, which would collide with the sender column.

Five behaviours change:

- **`/sql` and `/explain` answer `503` when the hot tip holds more than 64 MiB of row JSON**
  (`SQL_MAX_HOT_BYTES`), beside the 2,000,000-row cap they already had. They never answer from sealed
  data alone (#1376).
- **A `/sql` request that finds no free permit waits up to 250 ms for one** before it is told the node
  is busy, with at most 256 waiting per nest; past that it is refused at once, as before. The wait comes
  off the query's 30 s deadline. `/q/{name}` and `/explain` still refuse at once (#1383).
- **A seal cut is also taken at 64 MiB of row JSON**, and a provisional segment is final past 16 MiB
  (#1391). Rows under about 3.3 KB each reach the 20,000-row cut first, so event nests cut where they
  did. A range whose rows are larger seals into different segments than 3.7.0 wrote for it.
- **A document nest's fetch window is capped at 400 blocks** on every path, tip loops included (#1376).
- **`doctor` without `--address` re-probes against the busiest contract in a short sample** and prints
  both windows. Its JSON row gains four `discovered_*` keys and keeps every existing one (#1385).

**Downgrading to 3.7.0 is safe for an events-only nest and refused for any other.** After one start on
this release, a nest with `[[calls]]`, `[[ipfs]]` or `[extract]` records its full decode identity, and
3.7.0 compares that with the event registry hash and refuses to start. Run on Arbitrum with the
v3.7.0 release binary and a release build of this release's code: an events-only nest went from 3.7.0 to this release and back, keeping one registry
hash and starting each time; a nest with one `[[calls]]` was adopted by this release with the warning
above, and 3.7.0 then refused it. Keep a copy of the directory from before the upgrade if you might
need to roll back. 3.7.0 also ignores `cid_json_path`,
`json_match` and `[ipfs.rows]` without a word: on the QoS nest's configuration it generates four tables
where this release generates six.

**A fresh `[[ipfs]]` nest.** The QoS nest (`top_level_calls`, two `[[ipfs]]` declarations with
`cid_json_path`, `json_match` and `[ipfs.rows]`, `keep_content = false`) is accepted, and `nuthatch
schema` reproduces the `registry_hash` it commits. Its measurements are in the next three sections. One
thing is open: on the tip path it holds about 1 GB of RSS against a 370 MB peak memory footprint, and
what holds the difference is not attributed. One day of its chart query serves at the default
analytics memory; an eight-day span needed a 1 GB `NUTHATCH_ANALYTICS_MEMORY_LIMIT`.

## A CID inside JSON, from an event or a call (RFC-0037 slice 5, #1367)

Edge & Node's QoS oracle posts `submitQoSPayload(bytes)` to a DataEdge on Gnosis, and the argument is
JSON naming a CID. `[[ipfs]]` now takes `cid_json_path`, the key holding the CID, and `json_match`,
which resolves only the objects whose string fields equal the values given, so one declaration per
topic reads one contract. The source can be a top-level call's calldata as well as an event column.
Declining a document is declared intent and happens before any fetch. A row naming no CID is counted
in `nuthatch_nest_ipfs_unreadable_total` rather than left without a trace.

## Every document resolves, and only a proven one is stored (RFC-0037 slices 6 and 7)

The 64-fetch-per-window budget is gone (#1374, #1375). Every document is resolved out of band behind
the cursor, from a work list re-derived from the hot store, with retry and backoff and a recorded
give-up after 10 failures. Sealing holds below any block whose documents are neither stored nor given
up on, so a range never seals short of a document that could still arrive, and tip-following never
waits on a gateway. The tip loop stops committing windows while 16 documents are outstanding.
`--seal-direct` decodes top-level calls and resolves their documents too, and counts a failure exactly
as the resolver does. On Gnosis, 2026-09-07 resolved whole at 288 documents per topic, and a `kill -9`
mid-resolution lost nothing.

Multi-block documents are verified (#1373). A document is proven either by re-encoding its bytes in
Kubo's default layout, which costs no request and proves all 4,025 QoS payloads from 2026-09-06 to
2026-09-12, or by fetching its blocks as a CAR and hashing each against its CID before the DAG is
walked. An unproven document writes no row: it is counted in `nuthatch_nest_ipfs_unverified_total` and
retried, because a gateway that serves the blocks may answer later. A document over a size cap is given
up on at once and counted in `nuthatch_nest_ipfs_oversize_total`. `init` still accepts an unproven
document, loudly.

New series: `nuthatch_nest_ipfs_pending`, and `nuthatch_nest_ipfs_resolved_total`, `_given_up_total`,
`_unverified_total`, `_oversize_total`, `_unreadable_total` and `_rows_refused_total`, each with a
runtime-wide `nuthatch_ipfs_*` total.

## A proven document becomes typed rows (RFC-0037 slice 8, #1377)

The QoS nest parsed megabytes of JSON on every query, and one day of its rollups peaked at 3.86 GB.
`[ipfs.rows]` explodes a proven JSON document into one typed row per element at resolution, in a table
of its own, written in one transaction with the document and conditional on the row that named it. In
a block whose declarations have rows, documents take `log_index` `625_000..=625_999`, and each is
allotted its `max_rows` from `626_000` in slot order, so no key depends on which gateway answered
first. A document that does not fit its declared columns is refused whole and counted in
`nuthatch_nest_ipfs_rows_refused_total`. `keep_content = false` drops the raw JSON; the CID still names
the bytes every row came from. Rollups over typed rows are views, because RFC-0041 entities bind only
event tables. On Gnosis from block 48,119,000, with a `kill -9` mid-resolution, 576 of 576 documents
for 2026-09-07 resolved and verified, the nest's parity check passes, and one day of the chart query
serves at the defaults in 1.9 s.

## A seal cut is bounded by bytes (RFC-0028 §4, #1391, #1376)

A cut was bounded by rows and block span but never by bytes, and the tip path read the whole finalized
range to choose one. The QoS nest sealed 1,342 megabyte documents at 11.35 GB of RSS. A cut is now the
earliest of 20,000 rows, 64 MiB of row JSON and the span, all counted from the rows, so segments still
do not depend on `--window`. The bound is a constant rather than a setting, because a boundary an
operator could move would give two operators different segments over the same rows. The tip path
chooses a cut with a streaming scan, reads only that cut, and stops at a span end it already knows.

Block bodies for `top_level_calls` fetch in 20-block batches, four at once
(`NUTHATCH_CALL_BODY_CONCURRENCY`, ceiling 10). `maybe_seal` yields between segments, so SIGTERM
during a seal exits promptly.

Measured on the QoS nest from Gnosis block 48,119,000, release builds, `/usr/bin/time -l`.
`--seal-direct` peaked at 434,388,992 bytes of RSS and exited 0.14 s after a SIGTERM during the seal.
The tip path, re-measured on the merged head, peaked at 1,027,293,184 bytes of RSS with a peak memory
footprint of 369,935,608 bytes, exited 0.05 s after SIGTERM, and sealed 5,836,883 rows in 562
segments, through block 48,219,405 against a last block of 48,219,799. The window held at 400, and
3,399 documents were resolved, 14 pending and none unverified.

## Serving and authoring

- **`--cors <ORIGIN>` on `dev` and `serve`** (#1384), repeatable, or a single `*`. It answers preflight
  and allows `GET` and `OPTIONS`. Without the flag no layer is composed at all. A value that could never
  match an `Origin` header (no scheme, a trailing slash, `*` beside named origins) is refused at
  startup. It grants reach, not access: every guard still applies. A hot `upgrade` serves without CORS.
- **`--explorer <URL>` on `init` and `add`** (#1388) names a Blockscout instance for a chain nuthatch
  ships no root for. It is tried after Sourcify and before the built-in list, reads the v2 API, reports
  an unverified contract as unverified rather than asking for an Etherscan key, and is never written to
  the nest.
- **`init --from-subgraph` reads a local `subgraph.yaml`** and resolves its `file:` ABIs from disk
  (#1390). Before this a repository manifest's ABIs were silently dropped. A fetched manifest may not
  name a local file, and a local one may name only files inside its own directory, symlinks included.
- **`doctor` finds its own probe address** when `--address` is not given (#1385). On
  `rpc.gnosischain.com` the range-only floor recommended `--window 320`, and the re-probe 81,920. On a
  provider that refuses an unfiltered sample it prints the floor as before.
- **A runtime adopts a candidate dataset only when the registry hash its store recorded matches**, not
  only when its files recompute to the wanted identity (#1386). A dataset written under an older decode
  no longer spends the mount's single adoption on a store it can never start from.
