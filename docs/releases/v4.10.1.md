Nuthatch 4.10.1 fixes four defects. Nothing changes for a nest that is not affected by them.

## Fixes

- **A missing or zero block timestamp refuses the window.** A public Arbitrum endpoint,
  `arb1.arbitrum.io`, answers every log's `blockTimestamp` as `0x0`. From 3.11.0 nuthatch took
  timestamps from `eth_getLogs` when a node carried them, and until 3.13.2 cached that zero, so a
  window served by that endpoint stored 0 for every block it held (#1911: 1,132 such rows on the
  allocations nest, since replaced). The indexer never rejected a zero, only an absence, and a source
  that omitted a block still stored 0. Now any non-genesis block in a window that is missing from
  the timestamp map or at 0 refuses the window, and every ingest path retries it.
- **An authored entity no longer claims a block before the store has committed it.** Entities were
  fed a window before `commit_window`, so for a moment the entity's watermark ran ahead of what
  `/sql` could read, and a window whose commit then failed had still been folded. Entities are now
  bound before the commit and applied only after it succeeds (#1906).
- **A seed snapshot is complete through the publisher's seal watermark**, not the last block that
  held a row, so seeding a quiet nest from a mirror no longer re-scans everything since its last
  event. Each publishing nest rewrites its `_seed/seed.json` on its next pass.
- **The allocations nest's swap script** (`deploy/swap-allocations-nest-l1.sh`, #1882) refuses a
  staged index more than 2,000 blocks from production in either direction, and its rollback refuses
  unless production serves the recorded dataset and the staged unit is inactive.

## Compatibility and upgrade

Replace the binary and restart. There is no storage migration or re-index. A nest that holds rows
with `block_timestamp` 0 from the earlier defect keeps them; they are sealed and need a re-index.
