Nuthatch 4.1.1 closes the blocker and every high from the cold audit of 4.1.0, taken the day after
the SQL engine changed. Nothing in it came from a live nest: two readers went through the tree and
these are the faults both agreed on. One of them stops the process from a single `/sql` statement, so
take this release if a nest serves `/sql` to anyone you do not control. It is 4.1.0 plus the twenty
fixes below, a Wasmtime patch release, and corrections to the documentation.

## Compatibility and upgrade

Replace the binary and restart. There is no storage migration, configuration change, NID change or
re-index. A catalogue written by 4.1.0 is read as it is.

Six things answer differently, each a refusal or an error where 4.1.0 said yes:

- `/sql` refuses a statement nested deep enough to exhaust the planner's stack.
- `/graphql`, in a `graph` build, refuses more than 32 root fields, more than 8,000 requested rows, a
  statement over 16 KiB, or an `and`/`or` nested past 64.
- A cold `GET /entity` waits for an analytical permit and answers `503` when none comes free.
- The admin routes answer with the error when `mounts.toml` or the job table could not be written.
- A live mount is refused when it is named `health` or `nests`, or takes a chain past 32 authored
  entities. Both were already refused at boot.
- `nuthatch check` fails on a key that `mounts.toml`, `entities.toml`, `queries.toml` or
  `semantic.toml` does not read.

`SUM` and `AVG` over a `_dec` column now skip the rows the column itself reports as `NULL`. If a view
of yours sums one, read that section.

## One statement could stop the process (#1655, #1654)

A `/sql` statement of about 2 KB, a chain of binary operators, overflowed the planner's stack and
aborted the process, and every mounted nest went with it. The host now bounds expression depth on the
parsed statement before a session opens. Burrmill bounds the same tree itself and plans what passes
on an 8 MiB thread. The test refuses 1,000 terms and runs 64.

The deadline and the shutdown interrupt share that seam. An interrupt that arrived before the
statement armed its token was lost, and the engine reset the token on entry. Both are held now.

## Rows stored under the wrong hash (#1629, #1634, #1633, #1630, #1635)

A window's logs and the hash of its last block are two calls. When that block was replaced between
them, the fork's rows were committed under the hash the chain has now, the next reorg check found the
two equal, and the rows stayed and sealed. The checkpoint is read first, and a window whose kept rows
disagree with it is refused and asked for again.

On a runtime of several nests, three more:

- The shared cursor did not ask again for the tail of the previous window, as a single nest does, so
  a provider that answered a window short left those rows absent for good.
- A reorg rolled the nests back and kept the block-timestamp cache, so re-indexed blocks sealed with
  the timestamps of the blocks they replaced.
- A window that failed after its views were fed was retried with the views already holding it, and a
  transfer was credited twice until the next restart. A failure before the commit now retracts the
  fold. A failure after it leaves the fold, and the retry drops the rows the store already holds.

A seal-direct factory backfill resumed after a restart ran with an empty child registry and sealed
the rest of its range without those children. The registry is rebuilt from stored factory events
before the backfill continues.

## The sealed layer could count a row twice, or name a file that was gone (#1631, #1632, #1644)

Sealed segments are immutable, so each of these was a wrong answer for good.

- A crash between a seal and its watermark re-sealed rows a provisional segment had already folded,
  and the catalogue could not tell. A segment now keeps the hash of the bytes it was given.
- The watermark could be durable before the segment's bytes were. A segment is written to a
  temporary file, synced and renamed, and its directory is synced, before the watermark moves.
- A live reclaim of one dataset could delete a shared segment another dataset's seal was about to
  name. The seal holds the file until its manifest is installed.

## Work with no budget (#1650, #1657, #1652, #1658)

- A `SELECT` of wide cells built each 8,192-row batch in full before the 64 MiB result cap saw a
  row. A budgeted batch is 128 rows in the engine and is encoded 32 at a time. The test peaks at
  235 MiB.
- A cold `/entity` read and the unknown-table error path both scanned sealed segments with no permit
  and no deadline. The first takes the `/sql` gate. The second no longer rebuilds every view to
  explain a name that was never one.
- Burrmill's internal `__raw`, `__hot` and `__union` registrations could be named from a public
  statement, which stepped around the historical window. They are refused.
- One GraphQL document is one permit, one clock and one 64 MiB budget, with the limits listed above.

## Config and the admin API (#1656, #1638, #1639, #1640, #1641)

A misspelt key, `sq1 = "deny"` in `mounts.toml`, was dropped and its default used, which left `/sql`
open while `nuthatch check` passed. `check` now fails on it and names the spelling one edit away, and
loading the file warns.

An unmount could be overtaken by the mount job it had just reported absent. A lifecycle route
reported success when its write to disk had failed, and the restart restored the old table. A mount
named `health` or `nests` was accepted, persisted, and refused at the next boot, taking every nest on
the runtime down with it. The 32-entity ceiling was checked at boot and not on a live mount.

## A sum of `value_dec` is the values that fit (#1664)

`value_dec` reads `NULL` for a value too large for `DECIMAL(38)`. `SUM(value_dec)` nonetheless
counted those rows, so the sum disagreed with the column it was a sum of. The aggregate now reads the
column as a `SELECT` does. The README, the MCP tool text and the builder skill said to sum
`value_dec` without saying what it leaves out; they now say it is the values that fit, and that
`value_overflow` marks the rows it leaves out.

## Wasmtime 48.0.5

Seven RustSec advisories against Wasmtime 48.0.3 were published on the day of this release,
RUSTSEC-2026-0321 among them. The transform runtime moves to 48.0.5, the patch release that closes
all seven.
