Fixes a `--seal-direct` backfill over `[[ipfs]]` documents that paused without a word on a slow gateway
(#1399). On 2026-09-15 the QoS nest's backfill stopped for 14 minutes with no log line: a failed
document fetch was retried quietly, and its window could not seal until the document was decided. The
Graph's gateway took 29.86 s to serve a document it had not cached, against a 30 s timeout, and stalled
mid-body on two others that Pinata served in 4.6 and 6.1 s. Retries are now logged and counted, each
attempt gets a longer timeout, one document holds a seal-direct window for at most five minutes, and
every document given up on is recorded (#1411, #1413). A nest mounted into a running runtime is now held
to the single-endpoint concurrency cap that boot already applied (#1414).

## Compatibility and upgrade

Replace the binary and restart. **Storage identity, the NID and sealed segments do not change, and no
CLI flag, `nuthatch.toml` key, metric or `/ready` field is removed or renamed.**
`--ipfs-window-deadline` is `#[serde(skip)]` on `Config`, like `--ipfs` and `--poll-interval`, so it is
never written to `nuthatch.toml` and never enters the content address. A document given up on is
recorded in store meta under `ipfs_gave_up:`, the key 3.8.1 already wrote, and a seal-direct backfill
seals the same Parquet bytes with the record as without it. `src/blob.rs`, `src/pack.rs`,
`src/calls.rs`, `src/seal.rs` and `decode/` are untouched since 3.8.1. An interrupted seal-direct
backfill resumes from its saved watermark, and a window that had not sealed is fetched again, its
documents included.

Three defaults change, all in how a document is fetched:

- **A seal-direct window waits at most 300 s for one document.** Under `--seal-direct`, a document not
  fetched within `--ipfs-window-deadline` is given up on so its window can seal. In 3.8.1 it was given
  up on only after ten failed fetches, about half an hour. `--ipfs-window-deadline 0` removes the
  deadline, so a document is again given up on only after ten failed fetches. Waits between attempts
  on this path are now 2 s, doubling to 30 s. The resolver behind the tip has no deadline and keeps its
  5 to 600 s waits.
- **A request's timeout grows from 30 to 60 to 120 s** with each failed attempt, on the seal-direct
  path and the resolver behind the tip. It was 30 s on every attempt. Manifest import keeps 30 s.
- **Every retried fetch is a warn line** naming the CID, block, attempt, error and the wait. 3.8.1
  logged a resolver retry at debug and a seal-direct retry not at all.

**A nest mounted into a running runtime backfills one window at a time on a single-endpoint chain**
(#1414). In 3.8.1 boot capped a chain whose cursor had one RPC endpoint, but a hot mount's seal-direct
pass ran at the runtime's full `--concurrency`. It now counts the endpoints of its chain's source, as
boot does, and warns when it caps. A nest mounted at boot, or a runtime with two or more endpoints per
chain, is unaffected. Only how many windows the pass fetches at once changes: no flag, `nuthatch.toml`
key, `mounts.toml` entry or identity is involved, the endpoint count is held in memory from boot, and an
interrupted backfill resumes from its watermark as before.

**A document given up on is absent from sealed history**, as in 3.8.1, and under the deadline that can
happen sooner. It is now listed at `/ipfs/gave-up`. Nothing fetches it again: repair remains open on
#1410. For a gateway that is slow or stalls on some documents, the remedy is a second `--ipfs` gateway
rather than a longer deadline.

**Downgrading to 3.8.1 is safe, and may fetch some documents again.** 3.8.1 wrote a give-up as the bare
CID and counts a document as given up on only when the stored value is exactly that CID, so it reads
this release's JSON record as no record. It does not consult records for a range already sealed. A
document the resolver behind the tip gave up on, in a range not yet sealed, is pending again: 3.8.1
fetches it, and holds sealing below its block until it is fetched or given up on after ten attempts.
A second give-up overwrites the record with the bare CID, which this release still reads, without its
declaration, error or time.

## Changes

- **`nuthatch_nest_ipfs_retries_total`**, with the runtime-wide `nuthatch_ipfs_retries_total`, counts
  failed fetches that are tried again, on both paths.
- **`/ready` gains three fields.** `seal_direct_concurrency` is `{"requested", "effective",
  "capped_by"}`, where `capped_by` reads `single_rpc_endpoint` when one RPC endpoint held the pass to
  one window at a time, and is `null` for a nest not started with `--seal-direct`.
  `seal_direct_ipfs_window_deadline_secs` is the deadline, `0` for none. `ipfs_gave_up_documents`
  counts the documents given up on. In a runtime, a nest mounted at boot or hot reports the first two
  under the route it is served at, where that differs from the nest's own name.
- **`GET /ipfs/gave-up?limit=`** lists them in block order, 100 by default and 1,000 at most, each with
  its CID, block, slot, declaration, last error and time. A bare CID an earlier build wrote is listed
  with a `null` declaration, error and time. It reads the embedded store and the Postgres hot store
  alike.
- **A seal-direct pass says when its first window is slow to land.** It logs a note every 30 s until
  the first window lands, and its start line names the deadline and any concurrency cap.
- `resolve_abi_path` canonicalises the manifest home it compares against, not only the ABI file
  (#1406); `init --from-subgraph` already did and was not affected. `scripts/trino-contract.sh` refuses
  a bash older than 4 instead of passing on macOS without comparing anything (#1412). RFC-0056 and
  RFC-0058 are drafts (#1404, #1403), and the pull request reviewer is a bash and jq script (#1407).
