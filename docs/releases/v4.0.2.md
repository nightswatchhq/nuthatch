Nuthatch 4.0.2 fixes how one RPC error is read. An endpoint that refuses an `eth_getLogs` for
returning too many results, and says so under the JSON-RPC code providers also use for rate limits, was
treated as throttled and asked the same question again for good. It is 4.0.1 plus that one fix (#1621).
Take it if a nest uses `rpc.mevblocker.io`, which every mainnet nest created by 4.0.1 does, or an
Infura-style endpoint.

## Compatibility and upgrade

Replace the binary and restart. There is no storage migration, configuration change, NID change or
re-index.

## A result cap is narrowed, not waited out (#1621)

`rpc.mevblocker.io` answers an oversized `eth_getLogs` with code `-32005` and "query returned more than
10000 results. Try with this block range [...]". Nuthatch read any `-32005` as a rate limit, so it
retried the same range instead of narrowing to the one the endpoint had just suggested.

4.0.1 made that endpoint one of the two mainnet defaults, which is how this was found: a factory
backfill pointed at it alone sat on one range for over ten minutes. On the default pair the other
endpoint answers, so a nest keeps indexing but wastes a retry each time; in 75 seconds of a factory
backfill on 4.0.1 that was eight.

The code now decides only when the message names no size cap. With the fix, the same backfill against
that endpoint alone completes with no retries: 35,271 events and 232 pairs over blocks 19,000,000 to
19,010,000, the counts every other provider gives. Two runs, one machine.
