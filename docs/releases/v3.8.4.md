## Compatibility and upgrade

Replace the binary and restart. **Storage identity, the NID, configuration and sealed segments do not
change.** An upgrade never refuses a store: the first start records what the store covers instead of
verifying it.

**Startup refuses a store whose data no longer matches what `nuthatch.toml` covers (#1423, fixes
#1420).** Beside the registry check, a nest compares its chain and chain id, each contract's address and
start block, its factories and its extraction settings with a record kept in the store as
`indexed_coverage`.

- **The first start after upgrading records it.** A store that already holds data starts and logs that
  its coverage was recorded, not verified: if a contract's address or start block changed before the
  upgrade, this release cannot know, and will hold the store to whatever it finds on that first start.
- **From then on, an edit to the chain, a contract's `start_block` or address, the factories or the
  extraction settings refuses to start** a store that holds data. The message names each part that
  moved:

  ```
  this nest's stored data covers something nuthatch.toml no longer declares:

    contract `<alias>`: stored {...}, config {...}
  ```

  and ends: "Re-index from scratch to adopt the new configuration (remove `nuthatch.redb` and
  `segments/`), or restore the previous configuration to keep serving this data. RPC endpoints and the
  nest's name are not part of this check and may change freely."

- **A store holding no data yet records the new coverage rather than refusing it**, so an
  interrupted first index that has written nothing still adopts an edited configuration.
- **RPC endpoints and the nest's name are not checked**, because neither can change a stored row. Both
  still move the NID and the data identity, which `/` and `/nest` now show as `nid` and `data_identity`.
- **A reader compares but never writes.** `serve` and a query frontend refuse a real mismatch and record
  nothing; only the ingestion owner records coverage.
- **Copying a store to another machine:** read "Copying a stopped nest to another machine" in
  `docs/operators.md` first. A copied store carries its record with it, so it must be served under the
  configuration it was indexed under.

**Downgrading to 3.8.3 is safe.** 3.8.3 does not read `indexed_coverage` and leaves the record in place,
so a downgrade serves the store as before. A coverage edit made while running 3.8.3 is refused when this
release next starts, which is the point.

## Startup checks a store's data identity (#1423)

The registry hash covers what a nest decodes: contracts, events and columns. It does not cover which
blocks were read. An edited `start_block`, a re-pointed address, a factory added or an extraction
setting changed all leave the registry hash where it was, so a store indexed over one range would go on
being served under a configuration claiming another, with the gap reading as absent rather than as
missing.

A nest now records those parts as `indexed_coverage` in the store, versioned, and compares them on every
later start. A record written under an older version of the layout is re-recorded rather than refused,
so the check can be extended without stopping a nest that has done nothing wrong.
