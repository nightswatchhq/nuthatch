Nuthatch 3.12.0 changes nothing in the published binaries. Every change since 3.11.0 is behind the
`folds` cargo feature, which is off by default, and the release artefacts are built without it. A
3.12.0 binary or image indexes, seals and serves exactly as 3.11.0 does: the same rows, the same
segments and the same content addresses. It is a binary swap and a restart, and it is optional.

The release marks where RFC-0059, checkpointed folds, stopped. Chief parked RFC-0059 and RFC-0060 on
2026-09-26, after this work landed.

## Compatibility and upgrade

No CLI flag, `nuthatch.toml` key, route or metric changed in a default build. The NID and data identity
are computed as before.

## Behind `--features folds`

For anyone building from source with `folds`, or `graph`, which enables it:

- **Checkpoints from the seal loop (#1502).** `dev` writes each fold's checkpoint as sealing advances,
  beside the seal and never inside it, and resumes from the latest verified checkpoint on restart.
  In a folds build, `check` also verifies checkpoints: it recomputes one from its
  predecessor, or walks the whole chain from genesis.
- **Retention (#1503).** `[retention]` in `folds/folds.toml` keeps the latest checkpoints and one per
  span of blocks, and a read into history a horizon dropped is refused by name.
- **Head snapshots (#1513).** Reads at the head evaluate each fold once per head and share the result.
  Nothing is evaluated while nobody reads. `[snapshots]` bounds how many are retained, for how long,
  and in how many bytes. Nothing in `dev` reads them yet.
- A fold that reaches a view looking back into history is warned about at load (#1504), and the loader binds each
  fact table over one file per segment schema rather than every file, the cause of a 580 MiB load peak
  (#1508).

## Measured

On the Graph Network corpus, one warm process, every one of 88 hot heads read once: p99 99 to 115 ms,
at most 16 snapshots in 52.3 MB, peak RSS 262 to 275 MiB across four runs
(`docs/bench/fold-snapshots-thinkpad.json`).
