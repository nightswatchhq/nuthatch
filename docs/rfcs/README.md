# Nuthatch RFCs

Design documents for the post-skeleton phase. Numbered in build order; each states its
dependencies. Status lifecycle: **Draft → Accepted → Implemented → (Superseded / Parked)**.
For everything *deferred or not-yet-done* across the whole series, the source of truth is
**[the issue queue](https://github.com/nightswatchhq/nuthatch/issues)** - one issue per leftover, with
`parked` marking what is deferred by decision. [backlog.md](../backlog.md) explains how to read that
queue and records the standing decisions behind it; it no longer keeps a second list. For the bar a release must clear before it's pointed at a real
workload unattended, see the **[production-readiness checklist](../prod-readiness.md)**.
RFCs **0019-0023** derive from the **[Jul-Aug 2026 roadmap](../high-level-roadmap-jul-aug-2026.md)**
(strategy agreed 2026-07-21); their decisions log is the authority for the choices they encode.
RFCs **0032-0035** derive from the **2026-08-04 architecture session** with GraphOps, whose working
notes are unpublished; each of the four restates the decisions it encodes so it stands alone.
Build order for that set is **0032 → 0033 → 0034 → 0035**, and 0035 is the 2.0 release itself.
Statuses last reconciled against the [progress log](../progress-log.md) on 2026-08-04.

| [0032](0032-the-tenant-runtime.md) | The tenant runtime - retiring the roost, keying data by nest identity | 0012, 0021, 0026, 0027, 0019 | **Implemented** (slices 1-5; slice 5 shipped in v2.0.0, 2026-08-06 - `roost dev` and `roost.toml`-as-authored-config are gone, the word survives only in RFC history and the migration path). `data/<nid>` + `nuthatch migrate` (#320), dataset grouping + route fan-out (#323), the tenant column (#322), deferred collection + `nuthatch prune` (#324). | [0033](0033-nest-identity-and-derivation-grafting.md) | Nest identity and derivation grafting - editing a nest without re-indexing it | 0012, 0018 §1, 0013, 0019 | **Implemented** (slices 1-3, 5, 6; slice 6 shipped in v2.0.0, 2026-08-06 - `nest diff`/`nest upgrade` removed, breaking changes named and refused at mount time). Slice 4 **deferred** (its acceptance criterion cannot fail - authored views are not materialised, so a view edit never cost RPC for the view; what it *does* cost is the NID moving the dataset, which is early cutoff's job), Slice 5 adds a **data identity** beside the NID: a cosmetic edit moves the package identity, the data identity stays put, and the new NID **adopts** the existing dataset instead of re-indexing the chain. Building it **withdrew one of §3's three safe normalisations**: comma-versus-explicit join is not a renaming in DuckDB's AST, it moves a predicate between `where_clause` and `condition`. Canonicalisation runs on DuckDB's *own* parser so a second parser can never disagree with the engine in the permissive direction. Slice 3 found a second §4 hole: a **bare** `current_timestamp` parses as a `COLUMN_REF`, not a `FUNCTION`, so a function-only denylist misses it and caches a frozen timestamp - Trino #22533 in one line. Float aggregation is deliberately *not* in the static list (it needs type binding, not parsing); the determinism gate is the backstop. - answers R-1 with the Fable research pass. Content addressing means one edited character re-indexes everything, so a **per-derivation reuse key** sits below the NID: package identity and reuse identity are two axes, and whole-package identity over-invalidates by construction. Key = canonical plan ‖ inputs' keys ‖ **resolved source identity** (bind to `chain_id`/contract/ABI hash, never to a table *name* - `pg_stat_statements` hashes OIDs for this reason) ‖ range ‖ **engine+version** (DuckDB changed CTE semantics at 1.4) ‖ finality state. The matcher is **strictly syntactic**: equivalence is NP-complete under set semantics and *undecidable* under bag semantics, so soundness over completeness is forced, not chosen. **Early cutoff/backdating** (Nix CA-derivations, Salsa) is the big win and the thing Substreams lacks. v1 is whole-derivation reuse only - partial range reuse is where CALCITE-1984 lives. Subsumes `nest diff`/`nest upgrade`, moving breaking-change detection to mount time |
| [0034](0034-the-query-allowlist.md) | The query allowlist - a bounded public surface without a resync | 0032, 0016, 0012 | **Phases 1 and 2 implemented** (2026-08-05). Phase 2 puts the **author's ceiling** in its own `queries.toml` - authored, so in the NID, but deliberately *out* of the data identity, because a ceiling inside `nuthatch.toml` would move the data identity and force a full re-index on every security tweak, which is the exact cost phase 2 was sequenced behind early cutoff to avoid. A mount narrows within it, never widens: adding an unsanctioned name is refused, and so is **keeping a sanctioned name and changing its statement**, which a name-only check would miss. `sql = "open" | "deny" | "allowlist"` per mount, callers send a **name and typed arguments, never SQL**, and parameter types are `int`/`address` only because both have a total validating parse with no escaping hazard. Two config mistakes fail at load: queries declared while `sql = "open"` (the control would silently not apply) and `allowlist` with none. Bounding a surface also closes `/explain` on that mount (#293 for bounded mounts; open mode is still unbounded). - decision O-10, from chris. The `/sql` guards (concurrency 2, 30 s, 50K rows, 2M hot rows) are **node self-protection, not a security boundary**: they bound one query and say nothing about which queries a nest will answer. The mechanism is small; **where the allowlist lives is the decision**. Phase 1 ships it as **mount config**, so the NID is untouched, nothing re-indexes, and two tenants with different surfaces still share one dataset. Phase 2 puts an author's *ceiling* in the manifest, which a mount may narrow but never widen - and is **gated on 0033**, because after it a routine security tweak flips the NID. Carving the allowlist out of the NID was considered and rejected: one exception is how content addressing rots. Named parameterised queries only, never pattern-matching on SQL text |

Scope is **retire the roost + config surface cleanup + HTTP route/response review + remove `nest diff`/`upgrade`**. **SQLite was removed from the scope by measurement**, not preference: the whole case rested on DuckDB being able to `ATTACH` a SQLite hot store, and it cannot (`duckdb-rs` has no `sqlite` feature; `LOAD sqlite` needs a runtime download that non-negotiables 1 and 3 forbid), so redb stays. The `provenance` block is the one review item with a design question inside it, since grafting means a result may come from data a *different* NID produced. Explicitly **not** breaking: the nest bundle format, sealed segments, one-cursor-per-chain, and the single-nest developer experience. The stability commitment (#312) must be published *before* 2.0, not with it |

## Conventions

All RFCs honor [`CLAUDE.md`](../../CLAUDE.md) non-negotiables: single static binary, ≤2 GB RAM
CI budget, no phone-home, determinism in the core, `MIT OR Apache-2.0`. Measured numbers are cited from the
[README progress log](../../README.md); targets are labeled as targets, never as results.

Each RFC carries: status, author, date, dependencies, what it blocks, and the standard
Abstract / Motivation / Goals / Non-goals / Design / Implementation / Testing / Risks /
Alternatives / Open-questions structure (adapted where a doc is process rather than engineering).
