### A1 - pool the connection and re-run #986

#### First, what #986 actually measured

Before any number of mine: `docs/bench/rfc-0042-986-concurrency.md` attributes its flat throughput to
`analytics.rs` holding *"one cached read-only DuckDB connection per directory, taken under a mutex ...
so concurrent `/sql` against one nest **serialises**"*, and its harness comment says modelling DuckDB
without that mutex *"would measure an engine nuthatch does not deploy"*.

**`analytics.rs` does not hold a mutex across a query.** From `attempt()`:

```rust
let mut slot = duck_cache_lock().remove(dir);   // guard is a temporary; it drops here
...                                              // the query runs with no lock held
if interrupted.load(Ordering::SeqCst) { drop(slot); }
else { retain_duck_cache(duck_cache_lock(), slot); }   // re-taken, briefly
```

The lock is taken to **remove** the slot from the map and taken again to put it back. The query itself
runs unlocked. A second concurrent caller on the same nest therefore does not queue: it finds the map
empty and opens a **fresh** connection (`open_locked_duckdb`), so N concurrent queries mean up to N
live connections, each with its own `MEM_LIMIT` of 512 MB and `MAX_THREADS` of 2.

The harness that produced #986 (commit `e8a192e7`, `tools/df-gate/src/main.rs`) builds its own
`Arc<Mutex<duckdb::Connection>>` and takes the lock inside the timed closure, before `prepare` and
holding it until the last row is drained. That is a serialisation the harness constructed. It is not
the code path it names.

Separately, the shipped `/sql` surface has a constraint #986 does not model either: `serve.rs` holds a
`Semaphore` of **`SQL_MAX_CONCURRENCY = 2`** and acquires it with `try_acquire_owned`, so a third
concurrent request is **refused with 503 immediately** rather than queued.

So there are three candidate causes of a flat line, and #986 names the one that does not exist.

#### A1a - the controlled experiment

`tools/slice6-<id>/src/main.rs`. Every arm calls `nuthatch::analytics::query_guarded` against
`/home/pepe/slice6-<id>/horizon-nest` with identical SQL, guard (30 s, 50,000 rows), views and cache
behaviour. Only the concurrency discipline differs. Arms run forward then reversed at every client
count. 15 repeats per client per arm per order, warm-up discarded. Peak RSS by
`.github/workflows/footprint.sh`'s method - `ps -o rss=` at 1 Hz, maximum over the window - one arm per
process, so each peak attributes to one arm.

Query **`small`** = `SELECT count(*) AS n FROM tally__payment_collected` (474 segments, 68,449 rows,
~68 ms single-client) - the "many small concurrent reads" dimension RFC-0042 §9's amendment and
Appendix A.4 both name as the one that matters most and public benchmarks represent least.

Throughput, medians of the two orders (qps = served / wall; refusals counted separately, never folded
into either):

| clients | `mutex` | `gate2` (shipped) | `gate4` | `gate8` | `gate16` | `unbounded` |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 15.0 | 14.9 | 14.9 | 14.7 | 14.7 | 14.8 |
| 8 | **14.75** | 27.3 | 49.5 | **72.4** | 68.3 | 69.8 |
| 32 | **14.76** | 27.3 | 50.2 | 71.2 | **81.5** | 66.1 |

**The `mutex` arm is flat: 15.0 -> 14.75 -> 14.76 qps from 1 to 32 clients.** That is #986's finding
reproduced exactly - 40.3 -> 39.6 there, at that query's scale - on the same engine, the same data and
the same code path. Adding thirty-one callers adds no work done.

**Every arm without the mutex scales.** `gate8` reaches 72.4 qps at 8 clients, **4.9x** the `mutex`
arm; `gate16` reaches 81.5 qps at 32, **5.5x**. The engine, the connection handling and the view
definitions are byte-identical across those cells. The only thing that changed is whether one lock is
held across the query.

So the answer to A1's question is: **the flat ~40 qps is not an engine property.** It is a property of
one mutex, and that mutex exists in the benchmark harness rather than in nuthatch.

Refusals, because a gate's throughput is only half the story:

| clients | `gate2` served / refused | `gate4` | `gate8` | `gate16` |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 30 / 90 | 60 / 60 | 120 / 0 | 120 / 0 |
| 32 | 30 / 450 | 60 / 420 | 120 / 360 | 240 / 240 |

At 32 clients the **shipped** surface (`gate2`) refuses **450 of 480** offered requests - 94% - and
serves the remaining 30 at a healthy 71 ms p50. That is the shipped behaviour working as designed:
fail fast, do not build a backlog. It is emphatically not "DuckDB is slow under concurrency".

**Two things `unbounded` shows that a pool does not.** At 32 clients it is *slower* than `gate16`
(66.1 vs 81.5 qps) and its p50 is 488 ms against `gate16`'s 167 ms, while its peak RSS is
**1,323 MB against 632 MB**. Thirty-two simultaneous connections thrash; the throughput optimum on
this box is a bounded pool of roughly 8 to 16, not "no limit". So the finding is not "remove the
limit" - it is "the limit is set at 2 and the knee is nearer 8".

single-client row is the control: all six arms agree at 0.46 qps and 2,157-2,166 ms, a spread of
**0.4%**, well inside `noise-floor.md`'s 5%. Whatever separates the arms at 8 and 32 clients is the

#### The finding that stops this being a clean win: peak RSS

Small query, peak resident over each arm's window (medians of the two orders):

| clients | `mutex` | `gate2` | `gate4` | `gate8` | `gate16` | `unbounded` |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 87 MB | 87 MB | 88 MB | 90 MB | 88 MB | 87 MB |
| 8 | 212 MB | **132 MB** | 224 MB | 375 MB | 366 MB | 376 MB |
| 32 | 573 MB | **135 MB** | 220 MB | 387 MB | 675 MB | **1,313 MB** |

Heavy query at 8 clients: `gate2` 223 MB, `gate4` 412 MB, `gate8` 824 MB, `gate16` 828 MB,
`unbounded` 829 MB. The single 32-client heavy block that completed (`mutex`) peaked at **1,263 MB**
over its 1,043-second window.

Peak resident memory rises with permitted concurrency, roughly linearly in the number of queries in
flight, because each in-flight query holds its own connection with a 512 MB `MEM_LIMIT`. `serve.rs`'s
own comment predicted this before I measured it - *"the real DoS multiplier is concurrency, not any one
query"* - and the measurement is that comment's arithmetic.

**So `SQL_MAX_CONCURRENCY = 2` is an RAM-budget decision, not an oversight**, and the 5.4x throughput
the pool recovers is not free: it is bought at 137 MB -> 718 MB. Under the pre-registered rules this is a mix
of branch one and branch three - *the flat line is a deployment property* and *pooling improves but
costs memory* - which is why I did not treat the gating rule's first condition as cleanly satisfied,
and ran B3 rather than waiving group B on a rule that only half fired.

Three honest qualifications on those RSS figures, the second of which I got wrong first time:

1. They are the **harness** process, which holds the result buffers as well as DuckDB, not a
   `nuthatch dev` process.
2. **The 256 MB figure is not the budget.** `docs/benchmarks.md` is explicit that the `footprint` CI
   job is *"a tight tripwire on a deliberately small scenario (one nest, one event type, 8004 rows,
   256 MB); its sensitivity comes from being small"*. The product promise is CLAUDE.md
   non-negotiable 2 - **<= 2 GB per active-chain cursor** - enforced by `multinest-footprint.sh` at
   `MAX_RSS_MB=2048`. Measured against the ceiling that is actually a promise, none of the numbers
   above breaches anything. What they do say is that the analytical surface
   alone reaches **824-829 MB at eight concurrent heavy queries (about 41% of one cursor's entire
   budget)** and **1,313 MB unbounded at thirty-two (about 64%)**, on a single nest, before any of
   the indexing side of that cursor is counted - and a cursor is shared across every nest mounted on
   it.
3. The peaks for the short blocks were sampled at 1 Hz over windows of 1-3 seconds, which is one or
   two samples. Those are re-measured at 10 Hz below; the figures in the table above are the 1 Hz
   pass and the longer blocks (30-260 s) are the trustworthy ones in it.

What is engine-independent is the **shape**: RSS scales with the number of queries in flight, because
each in-flight query needs its own working memory. Whichever engine is behind `/sql`, concurrent
serving is bounded by the per-cursor budget rather than by the engine's architecture.

### C1. `analytics.rs` does not serialise concurrent queries. #986, #991 and slice 5 all say it does.

| claim | reality |
| --- | --- |
| `docs/bench/rfc-0042-986-concurrency.md`: *"`analytics.rs` holds one cached read-only DuckDB connection per directory, **taken under a mutex** ... so concurrent `/sql` against one nest **serialises**, whatever the engine does inside a single query."* | The mutex is taken to `remove()` the slot from the cache map and taken again to put it back. The guard is a statement temporary and drops at the semicolon. **The query runs unlocked.** |
| `docs/rfcs/0042-slice5-decision-input.md`, known cost 4: *"Any engine deployed as `analytics.rs` deploys DuckDB - one cached connection under a mutex - would show the same flat 40 qps."* | It would not. Measured: same engine, same code path, same data - 14.7 qps flat with a held mutex, up to 79.4 qps without one. |
| #991 (open): *"Throughput does not increase with load ... That is `analytics.rs`'s design, stated in its own comment (#295)."* | The design is the opposite. #991's issue 1 is an artefact of #986's harness. Its recommendation 1 - *"publish the ceiling ... expect ~40 qps"* - would document a ceiling the product does not have. |

**Where the belief came from.** `analytics.rs`'s own doc comment on `DuckCache` says *"The connection is
still read-only and still single-user; **queries take the mutex**, ingestion never writes here."*
Queries do take the mutex - twice, for a map operation each time. Two subsequent pieces of work read
that sentence as "queries serialise on the mutex" and published it as a measured property. Neither
checked the body of `attempt()`.

**Reproduction.** `tools/slice6-<id>`, arms `mutex` and `unbounded`, `CLIENTS=32`, `REPEATS=15`, against
`horizon-nest`; raw at `raw/a1a-conc.raw.log`. The two arms differ by one `Mutex<()>` and nothing else.

**Consequence for the decision.** The §11 concurrent-throughput row, as slice 5 fills it, compares a
harness-imposed serialisation against an unserialised Rust operator. It does not compare two engines.
That row cannot support a removal argument, and it never could have.

### C2. #991 attributes the figures to "the `/sql` path". They did not go through `/sql`.

#991 says *"`net_balances` over the `/sql` path"* and quotes #986's table. #986's numbers come from

distribution: `serve.rs` acquires its 2-permit semaphore with **`try_acquire_owned`** and returns a
`503` on failure, so a third concurrent caller is refused in microseconds rather than queued for
7 seconds. A p99 of 7,066 ms is not a shape that surface can make.

### C3. My own: the A1 mutex arm's first pass timed service time, not the caller's latency

### C4. My own: the harness first resolved a different DuckDB than the product links

## 6. What I think

### The strongest case for removal, stated properly before I disagree with it

It is a good case and it deserves to be put at full strength rather than in a form convenient to
answer.

Every empirical result this RFC has produced since slice 2 points one way. #987 built a specialised
Rust operator for the heavy fold and it was **faster than DuckDB at all twenty-four configurations**
(0.55-0.85x), parity exact. #996 ran real authored views on DataFusion over 38,428 real Lodestar
segments: **parity exact on 248,487 rows, 0.81-1.64x, faster on two of five including the largest**.
RFC-0041 shipped and moved the expensive panels out of general SQL entirely - `indexer_rewards` went
p50 2.15 s to 87.7 ms - so the surface a replacement must be fast at is smaller and skewed toward small
concurrent reads, which is where DataFusion's weaknesses matter least.

A4 now adds that the executor surface is **closed at twelve to thirteen stock relational operators**,
every one of which DataFusion implements natively, and that eighteen adversarially varied ad-hoc
queries add exactly one. And A1 removes the last row where DuckDB appeared to win: the flat 40 qps was
a mutex in a benchmark harness, so DuckDB has no concurrency advantage either - it simply never had the
disadvantage that was published.

Against that, removal buys the only two things slice 0 measured as large: **93% of native artefact
bytes** (245 MB of objects out of 264 MB), and **the sole reason a C++ runtime links at all**, which on
Linux is a real, checkable ABI floor at `GLIBCXX_3.4.29`.

And the reply to slice 0's "DuckDB is only 10.6% of build time" is fair: 10.6% is still 133 seconds and
`libduckdb-sys` is the largest single compilation unit in the tree at 132.1 s. That wasmtime and
cranelift cost twice as much is a *tu quoque*, not a defence. Two wrongs.

I do not think that case wins, and here is why.

### Reason 1: everything on the removal side is a spike, and the one piece of Rust that beat DuckDB shipped a defect in the exact class the RFC ranks first

Slice 5 already says it: *"Five of DuckDB's six roles have no implementation ... **Nothing has been
built**: every measurement here comes from `tools/df-gate`, deliberately outside nuthatch's dependency
graph."*

That is not a quibble about maturity. It is about what the measurements license. #987 is **one**
operator, for **one** fold, and its parity claim was *"exact parity, 24/24 configurations"*. On
2026-08-30 - the day before this run, on the commit I measured - #998 recorded that the same operator
negated debits with plain `-d` and accumulated with plain `+=`, so **`i128::MIN` overflowed on
negation and per-address totals wrapped silently in release builds**. The fix in `13ba548c` needed
checked arithmetic at **three** sites, and the third is the one nobody would guess: merging two
partials that are each in range can produce a sum that is not.

Twenty-four configurations of "parity exact" could not see it, because the corpus never reached the
boundary. It was found by review.

Appendix A ranks **exact-arithmetic divergence as gate risk number one**, *"high likelihood without
action"*. The first Rust operator built for this RFC realised that risk, in a bench harness, and the
parity corpus built to catch exactly this missed it. A composed §5.3 path needs a dozen such operators
plus a parser, a function-vocabulary classifier, a restart seed and an entity server, each with its own
boundary. Extrapolating from one operator's headline to six roles is the move slice 5's own correction
table exists to warn against - and two of those four corrections were caught by a reviewer rather than
the author.

I am not saying it cannot be done. I am saying nothing in the evidence tells us what it costs, and the
one data point we have is a defect per operator.

### Reason 2: the one concrete portability benefit is untested, and it is the only thing A3 was for

**A3 did not run.** So I cannot tell you whether `-static-libstdc++ -static-libgcc` removes
`libstdc++.so.6` from the release artefact's dynamic dependency set. That matters, because it is the
difference between two very different statements:

- if it does, then Tier 2's *entire measurable* portability payoff - the `GLIBCXX_3.4.29` floor slice 0
  found and #946 documented - is available today for two linker flags, and removing DuckDB buys
  nothing on that axis that a one-line change does not;
- if it does not, then the ABI floor is genuinely tied to DuckDB, and the portability argument keeps
  the one concrete form it has.

I have not measured it and I will not guess. What I can say is what the *other* half of A3 would have
tested and what A2 already found: **no platform the README lists fails today**, and **no named person
is blocked** on either outcome. So A3 moves my confidence and not my direction - which is why the
decision below is stated with a number rather than withheld.

The scripts are staged and it is a ten-minute run in the fast form. It should be the first thing done
when this resumes.

### Reason 3: the concurrency finding removes an argument from the removal side, not from the keep side

This is worth stating carefully, because A1's result looks at first like a point against DuckDB and is
the opposite.

Slice 5's known cost 4 credits the Rust path with an architectural advantage: *"The Rust path scales
because it has no shared connection."* A1 shows the comparison was against a mutex the harness built.
Take it out and **the same DuckDB, on the same code path, scales 5.4x** - from 14.7 to 79.4 qps. So the
Rust path's structural concurrency advantage over DuckDB-as-deployed was never real.

And the ceiling that does bind is engine-independent. Peak RSS rises with permitted concurrency because
each in-flight query holds its own memory budget, and `SQL_MAX_CONCURRENCY = 2` exists to keep the
analytical surface inside the per-cursor RAM budget - `serve.rs` says so in its own comment, and the
curve measured here is that comment's arithmetic. A DataFusion path serving N concurrent queries needs
the same per-query memory pool and hits the same **<= 2 GB per active-chain cursor** non-negotiable. The
binding constraint on concurrent serving is CLAUDE.md's footprint budget, not which engine is behind
`/sql`.

So after A1, the §11 concurrent-throughput row does not favour either engine. It favours fixing a
number in `serve.rs`, and it tells us the fix is bounded by RAM rather than by architecture.

### Reason 4: the costs of removal are named, specific and product-visible; the benefits are not

The cost side is not speculative. It is a list, and every item on it has a source:

| cost | source | why it is not a detail |
| --- | --- | --- |
| `HUGEINT` compatibility layer | #996: 4 of 5 real views needed rewriting to `DECIMAL(38,0)` | §3: *"Requiring users to rewrite valid Nuthatch SQL is a regression without a compatibility layer."* |
| Stricter ambiguity rules | #996: `port_queue` - qualified and unqualified `net_signal` in one schema; DuckDB accepts, DataFusion refuses | A valid authored view stops binding. Not mechanical. |
| Overflow semantics | DataFusion #17539, open: default arithmetic **wraps** where DuckDB errors | The number-one ranked gate risk, and #998 shows what it costs to hand-roll |
| The admissible function vocabulary | slice 0 §4: `entities.rs` classifies aggregates via `duckdb_functions()` | **A public contract.** It decides what a user may write in `entities.toml` |
| Alias canonicalisation in the parser | slice 0 §4 correction: `percentile_cont` is refused only because DuckDB's parser rewrites it to `quantile_cont`; pinned by `the_allowlist_depends_on_the_parser_canonicalising_aliases` (#969) | A replacement parser with different aliasing changes what the allowlist refuses, silently |
| The grafting engine string | slice 0 §4, `graft.rs` | Latent today. **After RFC-0033 slice 4 (#357) an engine change invalidates every reuse key by construction.** Swapping before #357 is free; after it, it is a full recompute per derivation |

Against that, §7 says: *"Expected wins include several of clean/incremental build, disk, binary size,
cross-compilation, containers, CI and native toolchain requirements. If these do not materialise,
removal needs stronger justification."*

Counting them honestly against what slice 0 and this run measured:

| expected win | materialises? |
| --- | --- |
| clean build time | **Partly.** 133 s of 1,257 s unit time, 10.6% - and wasmtime + cranelift, at 21.3%, stays |
| disk / `target/` | **Yes.** 245 MB of native objects, 93% of the total |
| binary size | **Yes**, and A3 quantifies it |
| cross-compilation | **No named beneficiary** (A2), and A3 tests whether the floor even needs DuckDB removed |
| containers | No evidence either way; nothing measured, nothing asked for |
| CI | Follows build time: partial |
| native toolchain requirements | Real on Linux, **nothing on macOS** (slice 0 §3a: `libc++` is always present at an OS-guaranteed version) |

Two of seven materialise clearly, both of them size. That is the "if these do not materialise" case §7
anticipates, and it says removal then *"needs stronger justification"*. The stronger justification would
have been performance or capability, and after A1 there is no performance row left that favours the
candidate over DuckDB-as-deployed.

### Reason 5: nobody is asking, and §11 forbids the arguments that remain

A2 found **zero named beneficiaries** across 347 tracker issues, one discussion, eight grant milestones
and the partnership record. No platform the README lists fails today. No funder deliverable names a
reproducible build, a static binary, musl or cross-compilation.

Strip out what §11 rules inadmissible - *"No appeal to a previous RFC, Rust purity, reputation,
roadmap or 'probably'"* - and what is left of the removal case is: 245 MB of build artefacts, one ABI
floor line in a README, and an aesthetic. The first is real. The second is what A3 measures. The third
is the failure mode §11 names first: **purity becoming the objective.**

RFC-0013 §2 named DataFusion the long-term destination on architectural grounds and made it
**benchmark-gated**; its 2026-08-02 gate failed at 1.6-2.7x. Nothing here says that direction is wrong.
What this run says is that the gate is still not met on the whole surface, that the cost of meeting it
is now itemised, and that the benefit on the other side has shrunk every time somebody measured it
rather than asserted it.

### What the gating rule says, and what I did with it

```
A1, A2, A3, A4
  if A1 removes concurrency AND A2 finds no beneficiary  -> KEEP; waive B
  if A4 shows an engine, not a layer                     -> KEEP; A4 is the blocker; waive B
  otherwise                                              -> B3 ...
```

- **A1 removes concurrency**, but on branch one *and* branch three at once: the flat line is a
  deployment property (branch one), and pooling recovers 5.5x while costing 135 MB -> 1,313 MB
  (branch three, *record the curve*).
- **A2 finds no beneficiary.** Zero named.
- **A4 shows a layer, not an engine.** Twelve to thirteen stock operators, closed under eighteen
  adversarial additions. So the second branch does not fire, and A4 is **not** a blocker - which is a
  point *for* removal being feasible, and I have counted it that way.
- **A3 did not run.**

So the gate's first condition fires, and its "waive B" would have applied. I had already decided to run
B3 anyway, because branch three fired too and B3 is the row that resolves it. It was cut for time
rather than waived on the rule, and the difference is recorded rather than tidied away.

## 7. Decision

`DECISION: KEEP DuckDB. CONFIDENCE: 78%.`

### The amendment text §11 requires

**Keep DuckDB, because these measured regressions remain:**

1. **Five of DuckDB's six inventoried roles have no implementation at all** (slice 0 §4; slice 5 known
   cost 3). Parser/canonicalisation, the aggregate-classification vocabulary, the incremental
   reference oracle, the restart seed and entity serving are unbuilt, and two of them - the
   `duckdb_functions()` classifier and the parser's alias canonicalisation - are **public contracts**
   that decide what a user may write in `entities.toml` and what the allowlist refuses.
2. **`HUGEINT` requires a compatibility layer.** 4 of 5 real authored views needed rewriting to
   `DECIMAL(38,0)` (#996). §3: *"Requiring users to rewrite valid Nuthatch SQL is a regression without
   a compatibility layer."* None is built.
3. **A valid authored view stops binding.** `port_queue` - DataFusion's ambiguity rules are stricter
   than DuckDB's (#996). One view, one lost capability, unresolved.
4. **Exact-arithmetic semantics are the number-one ranked gate risk and remain unmitigated.**
   DataFusion's default arithmetic wraps where DuckDB errors (#17539, open). The first specialised Rust
   operator built for this RFC realised that risk in its own code: #998, fixed in `13ba548c`, needed
   checked arithmetic at three sites, and a 24/24 "parity exact" corpus could not see it.
5. **General SQL over a realistic layout is 2.53-2.80x slower** (#964, re-run #981). §5.3 routes
   around it with a specialised operator, but that operator is one of the dozen not yet written.
6. **§7's expected wins do not materialise.** Two of seven - disk and binary size. Build time is 10.6%
   with a larger consumer left in place; cross-compilation has **no named beneficiary** across 347
   tracker issues, one discussion, eight grant milestones and the partnership record.

**And record what stopped being a regression.** The §11 concurrent-throughput row does **not** belong
on this list. It measured a mutex the benchmark harness built, not one nuthatch holds. Slice 5's known
cost 4 should be struck.

**Reopen condition** - a number and a date, both required:

> Reopen RFC-0042 **on or after 2027-09-01**, or earlier if **any one** of the following is recorded:
>
> - **a named user or funder deliverable** requires a musl, static or unlisted-platform build that the
>   C++ tail blocks (A2 found zero; one is enough);
> - **all five unbuilt roles pass their parity corpus inside a two-day box each** (RFC-0042 B1) -
>   at which point "nothing has been built" stops being an argument;
> - **DataFusion ships checked, erroring integer/decimal overflow by default** (#17539 closed), which
>   removes the number-one gate risk without a custom UDAF per aggregate;
> - **RFC-0033 slice 4 (#357) is scheduled**, because the ordering is asymmetric: swapping the engine

**What must happen anyway, whatever the engine, and is not blocked by this decision:**

- **Strike the false serialisation claim** from `docs/bench/rfc-0042-986-concurrency.md`, slice 5's

- **Revisit `SQL_MAX_CONCURRENCY = 2`.** The knee on this box is nearer 8, worth ~4.8x throughput, and
  the constraint that binds is the per-cursor RAM budget rather than the engine: unbounded at 32

## 8. What would change my mind

**One measurement: B1's spike on the two product-visible roles a DataFusion port does not address -
the parser/canonicalisation role (`entity_lower.rs`, `graft.rs`) and the aggregate-classification
vocabulary (`entities.rs`).**

They are the right pair because slice 0 §4a already answers the others: a DataFusion port addresses
`analytics.rs` outright and `seal.rs` is test-only. These two it does not touch at all, and both are
public contracts rather than implementation details.

**Threshold.** Both built, in Rust, with no DuckDB in the graph, passing the existing parity corpus for
that role - including `the_allowlist_depends_on_the_parser_canonicalising_aliases` (#969), the test
that pins `percentile_cont` being refused only because DuckDB's parser rewrites it - **within a
two-day box each, with no capability lost from `entities.toml`'s admissible vocabulary.**

If both clear that, my reason 1 collapses. "Nothing has been built" is doing most of the work in my
reasoning, and it is the kind of claim a fortnight of work can falsify. At that point A4's twelve
operators, #987's 0.55-0.85x and #996's exact parity stop being spikes and start being an
implementation, and I would expect to flip to REMOVE.

If either overruns its box, or loses a function from the vocabulary, or needs the allowlist's refusal
set redefined, that is the quantified blocker §11 asks for and the decision hardens.

**Second, smaller, and cheap: A3.** If `-static-libstdc++` does *not* remove `libstdc++.so.6`, the ABI
floor is genuinely tied to DuckDB and my confidence drops from 78% to roughly 70% - direction
unchanged, because A2 still finds nobody blocked by it. If it does remove it, 78% becomes about 85%.
It is a ten-minute run and it should be done first.
